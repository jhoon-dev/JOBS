# 기준선·실적·계획 대비 변경 비교

2026-10-26 · PRD-04/05, CAL-07/08 일부와 기간 관점의 F08/F09를 구현한다.
네트워크·달력은 현재 native FS0/동일 달력 범위를 유지한다. 실적 공수·물리 진척·원가는 별도 후속 범위다. 정률 배정의 잔여 수요·자원 가용성은 별도 [자원·평준화 창](resources-leveling.md)에서 검증한다.

## 사용 흐름

1. 프로젝트 시작일·작업·기간·FS 선행·휴일을 입력한다. 모든 작업 기간이 알려지고 순환/누락 참조가 없어야 한다.
2. **추적 → 기준선 저장**에서 이름·승인자·승인 사유를 입력한다. 현재 계획을 새 버전으로 고정한다.
3. **상태일 설정**에서 `YYYY-MM-DD HH:mm`을 정한다. 상태일을 선택하면 F9는 실적 반영 잔여 예측을 계산한다.
4. 표에서 작업을 고르고 **선택 작업 실적**을 연다. 실제 시작/완료, 실제 소요·잔여 근무분, 보고자·사유를 입력한다.
5. 완료는 실제 시작·완료와 잔여 0을 함께 입력한다. 미완료 작업은 실제 완료를 비워 둔다. 8시간은 480분이다.
6. 정정은 같은 화면에서 새 사유로 보고한다. 기존 보고는 아래 이력 표에 남는다.
7. F9로 최신 예측을 계산한 뒤 **계획 대비 비교**를 연다. 비교 기준선을 선택하여 현재 계획과 예측 편차를 나누어 확인한다.
8. 간트 기준선 선택 상자에서 기준선을 고르면 회색 막대가 겹쳐진다. 초록+[실제]는 완료 실적, [예측]은 실적 반영 예측이다.
9. `.jobs` 파일을 저장하고 다시 열면 기준선과 보고 이력이 유지된다. 현재 계산 cache는 F9로 재생성한다.

상태일을 과거로 돌리면 그때까지의 보고만 사용한다. 상태일을 해제하면 보고 원장을 보존한 채 현재 계획 모드로 돌아간다.

## 수동 검산 예제 · F09의 기간 부분

시작일 2026-10-26, A 기간 16h, 월–금 09–12/13–18, 휴일 없음.
기준선 이름 `최초 승인`, 승인자 `PM`, 사유 `초기 승인`으로 저장한다.
상태일을 2026-10-26 18:00으로 설정하고 A에 실제 시작 2026-10-26 09:00,
실제 소요 480분(8h), 잔여 960분(16h)을 보고한다.

| 항목 | 기대 결과 |
|---|---|
| 기준선 완료 | 2026-10-27 18:00 |
| 현재 계획 완료 | 2026-10-27 18:00 · 기준선 대비 0h |
| 잔여 재개 | 2026-10-27 09:00 |
| 실적 반영 예측 완료 | 2026-10-28 18:00 · 기준선 대비 +8h |
| 기간 진척 | 8/(8+16) = 33.333…% · 표시 33.3% |

현재 계획 기간만 20h로 바꾸면 계획 편차는 +4h, 보고된 잔여가 같은 예측 편차는 +8h다.
기준선은 계속 16h와 원래 날짜를 보존한다. 새 승인은 기준선 v2를 추가한다.
미보고 작업의 진척은 미정이며 0%로 간주하지 않는다.

## 불변 기준선

2026-10-30 응답성 보완: 화면의 기준선 승인은 비동기 편집 요청으로 처리한다. 전체 일정 계산·재검산과 승인 메타데이터/문서 검증, 저장 지점 대비 dirty 계산은 worker에서 끝낸다. GUI는 외부에서 변경할 수 없는 준비 결과의 문서 ID·revision·session·저장 지점·취소 여부를 확인하고 원자적으로 반영한다. 준비 중 편집·재열기·독립 저장은 오래된 승인을 반영하지 않으며 일반 저장이 요청 원본을 저장한 경우에는 승인을 이어서 반영한다. 취소 도구 모음으로 실행 중 승인을 취소할 수 있다. 승인 반영 후 기존 기준선·실적·원가는 보존하며 일반 undo 이력은 기존 승인 경계 정책에 따라 정리한다.

기준선에는 ID·이름·버전·승인자·사유·생성 UTC 시각·원본 문서 ID·입력 revision,
계획 입력(작업 ID/기간/관계/WBS/시작일/달력/휴일/정책), 고정 엔진 버전과 계산 결과를 저장한다.
현재 실제/예측을 승인 계획으로 섞지 않고 **현재 계획 입력으로 계산한 결과**를 동결한다.
기존 기준선을 수정·삭제하는 명령은 제공하지 않는다. 변경 승인은 새 버전과 새 승인 사유를 남긴다.
다른 이름 저장은 원본 문서 계보와 과거 스냅샷을 유지한다.

준비 계산은 불변 snapshot으로 worker에서 실행한다. 수신 시 현재 문서 ID/revision/입력과 다르면
저장을 거절한다. 저장 결과는 같은 고정 엔진으로 재검산하므로 checksum이 맞아도 입력/결과 모순을 거절한다.
승인자는 로컬 입력값이며 계정 인증·전자서명은 후속 범위다.

## 실적 원장과 정정

각 보고는 ID·작업 ID·상태일·기록 UTC 시각·보고자·사유·이전 보고 ID·원본 문서 ID/revision·
보고 당시 계획 기간·실제 시작/완료·실제 소요/잔여 근무분을 저장한다. 실제와 잔여를 계획 기간으로 자동 환산하지 않는다.
새 보고/정정은 append-only다. 같은 작업의 이전 이벤트를 연결하고 원본 필드와 기록을 유지한다.
조회는 상태일 이하의 가장 늦은 보고일을 사용하고, 같은 보고일이면 나중에 기록한 정정이 우선한다.
과거일 정정이 더 나중 상태일의 보고를 대체하지 않는다. 보고 당시 계획 기간도 현재 계획 변경으로 바꾸지 않는다.

미래 실제, 완료<시작, 실제 소요/잔여 음수, 완료인데 잔여>0, 진행 중인데 잔여 0,
기간이 있는 미착수 작업의 잔여 0, 보고자/사유 누락 등은 오류로 거절한다. 실패 시 원장/revision/저장 상태는 유지한다.
실제 소요 **기간**이 시작부터 완료/상태일까지의 civil 경과시간을 넘는 입력도 거절한다. 다인 공수와 기간을 혼합하지 않는다.
완료 작업의 실제 날짜가 상태일보다 과거여도 현재로 이동시키지 않는다.

## 예측 정책 · retained-remaining-v1

계획 CPM은 `plan-asap-v1`, 상태일이 있는 결과는 `retained-remaining-v1`로 구분한다.
현재 native profile은 먼저 현재 계획의 기간·참조·순환을 검사하며 불완전/충돌이면 전체 예측을 반환하지 않는다.
실제 완료 작업은 관측 시작·완료를 고정한다. 미완료 잔여는 상태일과 선행 예측 완료 중 늦은 시각 이후에 배치한다.
이미 시작한 작업은 실제 시작을 보존하면서 남은 부분에 FS 논리를 유지한다.
미보고 작업은 현재 계획 기간을 잔여로 사용하며 `UNREPORTED_REMAINING`과 보고 범위를 표시한다.

실제 후행 시작이 선행 완료보다 빠른 out-of-sequence는 `OUT_OF_SEQUENCE`로 드러낸다.
실제 날짜를 이동하지 않고 잔여를 선행 예측 완료 이후로 배치한다. 간트 예측 FS 선은 잔여 재개 지점에 연결한다.
F08의 native 근무분 예제: 상태일 12h(2026-10-27 14:00), A 실제 8h/잔여 8h → 완료 20h,
B 실제 시작 4h(2026-10-26 14:00)/잔여 4h → 잔여 20~24h. 과거 실제와 FS 불일치 진단을 보존한다.

예측은 여유·임계를 산정하지 않는다. 표에서 —/예측/실제 완료로 표시하며 자원 타당성도 미검증이다.
근무시각은 시간대 없는 civil 표현이다. 상태일 입력기는 OS 시간대 변환 없이 같은 시각을 저장한다.
프로젝트 시작일부터 20×366일 이내가 초기 계산 범위다. 범위 밖 실제/상태일은 원장에 보존하되 예측 충돌로 반환한다.
야간·다중 달력·DST·progress override·분할 실적 원장·공수·물리 진척은 후속 범위다.

## 비교 의미

비교 표는 기준선/현재 계획/실적 반영 예측의 시작·완료, 실제 시작·완료·소요/잔여,
기간 진척, 계획 완료 편차와 예측 완료 편차를 나란히 표시한다. 전체 프로젝트 완료 편차도 구분한다.
편차는 **선택 기준선 달력의 근무분** 차이를 시간으로 표시한다. 양수는 지연, 음수는 앞당김이다.
휴무일만 바뀐 날짜는 근무시간 편차가 0일 수 있으므로 실제 날짜도 함께 확인한다.
기준선 없음·작업 추가/삭제·계산 실패·비교 달력 범위 밖은 편차 미정(—)이며 0으로 표시하지 않는다.

작업 ID로 대응시켜 이름·계획 기간·FS 선행·WBS 소속 변경과 추가/삭제를 표시한다.
달력/휴일·시작일·WBS 정의 변경은 프로젝트 변경으로 표시한다. 선택 작업 상세에서 전후 입력을 확인한다.
기간 진척은 실제 소요/(실제 소요+잔여), 완료 보고는 100%이며 공수/물리 진척과 혼합하지 않는다.
전체 진척률은 만들지 않고 상태일 기준 보고 작업 수/전체 작업 수를 표시한다.

공수 기준 작업의 기준선 기간은 동결된 작업 달력·분할·시작/완료에서 산출한다. 현재 계획에서 삭제된 작업도 같은 값을 표시하며, 명목 기간이 없거나 공수에 따른 실제 기간과 달라도 기준선 기간을 바꾸지 않는다.

## 파일·검증 범위

schema 4는 `baselines`, `progress`, `statusAt`을 추가한다. schema 1/2/3은 기존 ID·입력·WBS를 유지해 읽고
새 추적 필드만 빈 값으로 채운다. 저장은 새 이름의 schema 4 사본으로 수행하여 이전 bytes를 보존한다.
64 MiB JSON 단일 파일/원자적 교체 계약을 유지한다. 화면의 승인 재검산은 위의 worker 경로를 사용한다. 원시 Baseline을 받는 동기 API와 파일 열기/저장/복구의 재검산은 유지하며, 큰 원장/다수 기준선의 파일 I/O·수신 검증 비용 최적화는 후속 범위다.

- `tracking_contract`: F09 +8h, 기준선 불변/버전·계획/예측 분리·달력 동결, F08 retained logic,
  상태일/정정 조회·완료 실제 고정·모순 입력 원자 거절·미정/읽기 전용.
- `tracking_file`: 전체 원장/스냅샷 왕복·사본 계보·checksum 재생성 후에도 모순 기준선 거절·schema 3 원본 보존.
- `tracking_ui`: 기준선→상태일→실적→+8h 비교·미보고 coverage·기준선 선택/겹침·모순 오류·정정·새 승인 버전·저장/재열기.
- `baseline_async_contract_ui`: 불투명 worker 준비/승인 반영, GUI 반영의 계산 checkpoint 0개, 기존 승인·실적·원가 보존, 일반 저장/재열기/독립 저장·중복 반영·읽기 전용·실패·사전/실행 중/반영 직전 취소, 1만 작업 UI heartbeat와 반영 시간 표본. 실행 옵션 `--xer <경로>`로 같은 1만 작업 XER를 사용해 측정할 수 있다. 시간 표본은 환경별 관측이며 보편적 지연 상한을 뜻하지 않는다.

2026-10-30 로컬 Windows / Qt 6.8.3 / MinGW Release / offscreen에서 기존 합성 1만 작업 XER(`industrial-campus-10000.xer`, SHA-256 `8f6236ad4f6c90b6e35f47179ac451f05ced3cc913f72c31f8ae235abc19ee6c`)로 위 테스트를 실행했다. 승인 전체 5,056ms, GUI의 문서 반영 0.2195ms, 5ms heartbeat 394회·최대 간격 31ms를 관측했다. 문서 반영 시간은 최종 검사부터 Edited 알림까지이며 이후 표·간트 갱신 전체 시간과 구분한다. 이전 점검의 동기 `appendBaseline` 3,724ms 구간은 현재 GUI 경로에서 worker 준비로 이동했다. 동기 API 자체의 재검산은 유지한다. 단일 표본이며 실행 순서/OS 캐시를 통제한 성능 보장으로 해석하지 않는다.

최종 제품의 전체 실적·기준선 요구, 상용 제품 동등성 및 우월성 검증은 별도 단계로 이어간다.

자원 증분(schema 5)에서는 기준선 입력에 자원·배정도 동결하며, 비교 표에 자원 정의/가용량·작업별 배정 변경을 표시한다. 기존 schema 4 기준선의 원본 보존 사본 이관과 재검산을 유지한다.

후속 원가 증분(schema 6)에서 단가·고정비·성과 측정법도 기준선 입력에 보존한다. 실제원가/물리 진척은 별도 불변 보고 원장으로 기록하고 [EVM 분석](costs-evm.md)에서 조회한다. 기간 진척을 물리/원가 진척으로 대체하지 않는다.
